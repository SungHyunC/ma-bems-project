# MA-BEMS · 멀티에이전트 건물 에너지 관리 시스템

[English](README.md) · 한국어

**라이브 대시보드: https://sunghyunc.github.io/ma-bems/**
(공개 사이트 배포 저장소는 [SungHyunC/ma-bems](https://github.com/SungHyunC/ma-bems), 이 저장소는 프로젝트 전체 원본)

6개 에이전트(코디네이터·HVAC·조명·태양광·ESS·EV 충전)가 15분마다 관찰→계획→조율→실행→검증을 반복하고, 부딪히는 계획은 코디네이터(v2)가 우선순위와 비용 기준으로 정리하며
가상 캠퍼스(Helio Campus)의 피크·요금·쾌적을 함께 관리합니다. 같은 날씨·재실·EV·DR 신호로 룰 기반 BMS를 나란히 돌려
차이만 비교합니다(반사실 그림자 실행). 고려대 세종 2026-2 기업연계형 캡스톤디자인 출품작입니다.

## 결과 한눈에 (시뮬레이션 기준, 9일 × 1분 단위, 1~8일 채점)

± 읽는 법: 입력이 고정된 한 번의 실행에서 "± 0.2"는 그 8일 일별 값의 95% 구간(t)이라 **일별 변동만** 뜻합니다. 입력이 달라져도 유지되는지는 시드 10회(`?seed=N`: 재실·EV·DR 시각을 다시 뽑고 날마다 날씨가 달라짐)의 실행 간 95% 구간이 맞는 척도입니다.

**코디네이터 v2가 기본값입니다**(2026-11-12). 이전 버전 v1은 `?coord=v1`로 정확히 재현되며, 아래 표의 대괄호는 v1 값입니다.

| 항목 | 에이전트 vs 룰 기반 BMS |
|---|---|
| 전력량요금 절감 (기본 BMS) | **17.4 ± 0.1%** [v1 16.7%] (1회 실행, ± = 8일 일별 변동). 시드 10회 **16.9 ± 0.2%** [16.5%] (실행 간 95% 구간) |

| 센서 BMS (에이전트와 같은 재실 센싱 + ESS 피크 제어 + 고정 DR 대응) | **10.5 ± 0.3%** [9.7%] (시드 10회 10.5 ± 0.2% [10.2%]). 그 BMS의 쾌적은 97.0%(시드 97.4%)로 낮아짐. `dr=off`에서는 15.0% [14.4%]라, 17.4% 중 약 2.4%p는 DR 미대응 효과 |

| 기본요금 (한전 8,320원/kW·월, 기간 최대 기준) | 기본 비용에는 없음. 넣으면 한전 요금·모델 부하 15.7 → 16.2%, BDG2 부하 형태 14.7 → 15.7%. 저장소에 달러 요율이 없어 달러 계산은 매개변수 |

BDG2는 미국 대학 건물 4개의 여름 평일 하루 실측 비-HVAC 전력을 헬리오 캠퍼스에 맞춰 크기를 조정해 매일 반복한 것이며, 이 캠퍼스의 실측 부하가 아닙니다.

- **구성요소 기여**(%p, v1은 대괄호): 실 단위 13.4 [12.3], ESS 3.6 [3.2], 공조 2.5 [2.2], 조명 0.9 [0.7], EV 0.1 [0.0]. 코디네이터의 배분 단계는 평상시 추가 절감이 없습니다(−0.16 [−0.15]; v2에서 `ablate=COORD`는 비용 기반 배분만 끄고 예측 기반 배터리와 DR 사전 냉방은 남음). 한도가 빠듯할 때 효과가 납니다. 초과 전력(코디네이터 있음 vs 없음): 900 kW 18 vs 37 kWh(−52%), 850 kW 392 vs 765 kWh(−49%), 800 kW 2,493 vs 3,282 kWh(−24%). v1은 417 vs 482, 1,675 vs 2,129, 4,610 vs 5,083 kWh였습니다.
- **코디네이터 v1 → v2** (v2는 2026-11-12 사용자 결정으로 기본값): v1은 우선순위 조율. v2는 DR 예고 + 배터리 예비·DR 뒤 단계적 복귀, 예측 기반 ESS 배분(미래 데이터 미사용), 에이전트 사이 비용 기반 배분(최대 3라운드)을 더했습니다. 기본 설정 70개 실행을 다시 돌렸고 `coord=v1`은 이전 결과를 그대로 재현합니다(`build/results/v1/`). v1 → v2: 평상시 16.7 → 17.4%, 시드 10회 16.5 → 16.9%(짝지은 차이 +0.4 ± 0.1%p, 기간 최대 −66 ± 26 kW), 폭염 13.7 → 15.4%, 최악의 날 9.8 → 15.9%·평균 최대 수전 1,512 → 1,299 kW(BMS 1,454보다 낮음), 한도 850 초과 1,675 → 392 kWh, 한도 800 기간 최대 1,157 → 950 kW. **나빠진 곳**: 한도 초과 시간(폭염 2,050 → 3,303분, 최악의 날 3,557 → 5,349, 한도 800 2,059 → 3,867), 한도 850 절감 −0.6%p, EV 몰림 평균 최대 수전 960 → 976 kW, 평상시 DR 이행 142 → 139%, 고장 훈련 추가 에너지 +1,572 → +1,605 kWh.
- **시나리오별 비용 절감** (v2): 폭염 15.4%, 흐린 날 14.3%, DR 19.1%, 한도 850 17.3%, EV 몰림 17.9%, 휴일 25.9%, 최악의 날 15.9%(v1 9.8%). 최악의 날 평균 최대 수전은 BMS 1,454 kW보다 낮은 1,299 kW입니다(v1은 1,512 kW로 BMS보다 높았음).
- **고장의 에너지 영향** (`?faultImpact=1`, 9일, 진짜 경보만 승인하는 운영자): 드리프트 고장은 감지 끔 +1,289 kWh, 켬 +26 kWh. 3시간마다 고장을 넣는 훈련은 감지 끔 +12,441 kWh(주입 49건) vs 켬 +1,605 kWh(주입 63건)라 같은 고장 수의 비교는 아님. 한계: 가상 센서에는 피드백이 없어 방치한 고착은 406 kWh를 아끼지만 불쾌 1,963 °C·h가 늘고, 닫힌 루프에서 드리프트 감지는 55 → 245분(중앙값)으로 늦어지며 훈련에서 오경보 55건.

시나리오 9종(폭염·흐린 날·DR·한도 하향·EV 몰림·휴일·센서 고장·최악의 날)별 결과와 한계는 [eval/README.md](eval/README.md).
절감은 아직 계량 데이터로 보정하지 않은 시뮬레이션 값입니다. 화면 캡처는 이 변경(코디네이터 v2 기본값) 전에 만들어져 예전 문구·수치(예측 11.0%, 절감 16.7% 등)가 남아 있을 수 있습니다(설명서 PDF와 데모 영상은 2026-11-12에 v2 기준으로 다시 만듦).

## AI 비서와 파인튜닝: 측정한 것과 못 측정한 것

- 파인튜닝 v2.2(2026-11-12, 사용자 결정으로 v2.1 대신 채택). 새 기본 협조 제어기에서 모은 학습에 쓰지 않은 세트, v2.1 → v2.2:
  채팅 수치 검사 93.3 → 97.1%, 답마다 정답에 없는 숫자 1.45 → 0.38개, 제안 정밀도/재현율(값까지, 모델만) 62.1/70.0 → 83.5/78.3%,
  "바꿀 필요 없음" 9.6 → 87.2%, 입력한 요청 49.8/55.6 → 65.7/62.2%.
  실제 질문 47개 × 3번의 점검 통과는 약간 낮습니다(옛 스냅숏 6개 제외 92.7 → 91.1%, 전체 80.9 → 79.4%).
- 알려진 한계(그 차이의 대부분): "왜 배터리를 방전하고 있어?"에서 v2.2는 ESS 에이전트의 계획 방전량 175 kW를 현재 출력("지금 ESS는 175 kW")으로 말합니다. 실제 출력은 분 단위 피크 가드가 올린 228.7 kW였고,
  게이트웨이의 수치 검사가 그 문장을 잡아 운영에서는 경고가 붙습니다. 다음 데이터 반복에서 고칩니다. v2.2는 현재 대시보드의 맥락 블록에 기대므로 공개 사이트가 현재 `index.html`이어야 합니다.
  운영 PC는 사용자가 합치기·`ollama create`·`.env` 변경을 하기 전까지 v2.1 그대로입니다([ft/README.md](ft/README.md)).
- 정리: 66개 실제 질문은 수정을 맞춘 회귀 세트이고 그중 1개는 v1 학습 데이터에 있었습니다. 학습에 Claude 출력은 쓰지 않았습니다.
- 이전 측정(v2.1, 학습에 쓰지 않은 조건 234건)의 "조건"은 새롭지만 질문 문장 234건 중 226건은 학습에도 있습니다. 처음 보는 문장 세트(`eval_gen`, 234건, [ft/README.md](ft/README.md))에서 v2.1은 수치 검사 99.1%, 핵심 숫자 96.4%, 한 문장 지시 100%, 답할 수 있는 질문 거절 0.4%.
- 수치 검사는 숫자가 모델에 준 데이터에 있는지만 보며 정확도 측정이 아닙니다. 질문 뜻 이해도 재지 않습니다.
- 실제 예상 질문 66개(41.5 → 62점, 오답 17 → 0)는 수정을 이 질문에 맞춰 한 회귀 세트라 일반화 점수가 아닙니다.
- 게이트웨이: `/v1/chat/completions`는 관리자 키 전용, 프롬프트 추출 검사는 모든 작업에 적용, 로컬 포트는 Origin·Content-Type 검사, 스트리밍 전 유출 검사, "한도를 넘을까?"는 예측 경로로 답함. `numcheck`는 숫자를 라벨에 묶고 잘못된 숫자 형식을 거절합니다(저장된 v2.1 출력의 통과율은 모든 세트에서 같고, 66개 실제 질문에서는 실제 오류 3건을 새로 잡았으며 1건은 저장된 문맥이 달라 판정 못 함). `server/test_gateway.py`에 테스트 8개.

| `deck/` | 경진대회 발표자료 원본(슬라이드 HTML) |
| `docs/` | 프로젝트 설명서(PDF·HTML). 데모 영상 파일은 용량 때문에 Releases에 둠 |
| `demo/` | 데모 영상 제작: 대본(`script.json`), 한국어 음성(`tts.ps1`), 자동 녹화(`record.mjs`), 합성(`assemble.py`) |
| `data/` | BDG2 실측 샘플(CC BY-SA 4.0) |

## 실행

```
python -m venv .venv && .venv\Scripts\pip install anthropic
copy .env.example .env          (ANTHROPIC_API_KEY 등 채우기, Ollama에 qwen3 8B 모델)
.venv\Scripts\python server\mabems_server.py      → http://127.0.0.1:5178
```

AI 비서 없이 보기만 하려면 `index.html`을 정적 서버로 열어도 됩니다(시뮬레이션은 브라우저에서 동작).
